# Implementation Tasks: TD Web GUI

Bite-sized tasks derived from [TECH_PROPOSAL.md](TECH_PROPOSAL.md), ordered **vertical-slice-first**: build the thinnest end-to-end path, then deepen it. Each task is scoped for a single focused session.

## How to use this doc

- Work tasks in order within a phase unless a task notes it's independent.
- **Hard dependency: Phase 1 → Phase 2 → {Phase 3, 4, 5}.** Within Phases 3/4/5 most tasks are independent and parallelizable.
- Every task lands its own Vitest coverage where testable. The proposal explicitly wants the connection manager, message parsing, throttle, and echo-suppression logic unit-tested.
- The wire contract is exercised against a **mock TD WebSocket server** (Phase 2.6), not a live `.toe`. The reference `td/` project (Phase 6) is the manual end-to-end check.
- `td-core` ships **zero CSS** and `solid-js` is a `peerDependency` — never bundle Solid.

## Phase 2 — Vertical slice: text & numbers over WebSocket

Minimal end-to-end. **No** reconnect, throttle, backpressure, watchdog, or heartbeat yet — those are Phase 3.

- [x] **2.1 — Wire-format types.** TS discriminated-union envelope for the *subset only*: `hello`, `welcome`, `snapshot-request`, `snapshot`, `update`. Include a `parse(raw): Message | null` that try/catches bad JSON and drops unknown `type`s.
- [x] **2.2 — `createTDConnection(url)` core.** Open WS; run handshake (`hello` → await `welcome` → `snapshot-request` → apply `snapshot`); apply inbound `update`; `send()`; reactive `status` signal (e.g. `connecting`/`open`/`synced`). **Lazy signal allocation:** `signal(name)` creates-or-returns one signal per name; routing table maps name→signal; inbound updates for unbound names are dropped (map miss, no allocation). Usable standalone with zero context.
- [x] **2.3 — Factory + context.** `createTDClient<Schema>()` returns a schema-bound bundle (`{ Provider, signal, ... }`). `<Provider url>` owns one connection and shares it via Solid context. `createTDSignal(name)` binds to the nearest provider's connection.
- [x] **2.4 — `TextInput`, `NumberInput`, `RangeInput`, `Value`.** Bound via `createTDSignal`; optimistic local write + send-on-change. `NumberInput`: hold-last-valid while empty/unparseable, snap-back on blur, clamp to `min`/`max` before sending, never send `NaN`. `RangeInput`: slider bound to a number param; value always in-range so no empty/`NaN`/clamp handling. `Value`: read-only, never sends, optional `format` fn, works for scalars and arrays.
- [x] **2.5 — Focus-based echo suppression.** Track an active-editor **count** on the signal (increment on focus/drag-start, decrement on blur/drag-end); suppress inbound TD updates while count `> 0`. Local edit wins while focused.
- [x] **2.6 — Mock TD WS server + integration test.** Stub WebSocket server doing `welcome` → `snapshot` → `update`; test the full `hello`→`welcome`→`snapshot`→`update` flow plus a malformed-message case.
- [x] **2.7 — Example wiring.** `apps/example/src/td.config.ts` exporting `{ id, url }[]` (host/port overridable via `import.meta.env`), plus a page with a text + number control bound through a provider.
  - *Phase done when:* the example round-trips a string and a number against the mock (or a hand-run TD).

## Phase 3 — WebSocket hardening

All tasks are per-connection options with sane defaults, not wire-format changes. Mostly independent of each other.

- [x] **3.1 — Reconnect + exponential backoff.** ~500ms start, double to ~10s ceiling, with jitter. Re-run the full handshake + snapshot resync on each reconnect.
  - *Note:* per-connection options `reconnect` / `backoff.{min,max}`. Half-jitter (`base/2 + rand·base/2`). Each attempt gets a monotonic `attemptId`; a torn-down socket's late `close`/`error` events guard on it, so a stale event can't drive a second reconnect.
- [x] **3.2 — Handshake watchdog.** Require `welcome` **and** `snapshot` within ~5s of `onopen`; otherwise abandon the attempt → backoff. Cleared the moment `snapshot` applies (`synced` flips true).
  - *Note:* the watchdog is armed **before** `hello` is sent — a TD (or the in-memory mock) that replies synchronously can complete the whole handshake inside the `hello` send, and arming after would leave a watchdog `onSynced` already ran past, firing a spurious reconnect.
- [x] **3.3 — `ping`/`pong` heartbeat.** App-level `ping` ~every 5s; a missing `pong` within ~10s marks the socket half-open → forces reconnect. (Guards an *established* session only — the watchdog covers the pre-handshake window.)
  - *Note:* the pong deadline is armed only on the *first* unanswered ping, so when the interval is shorter than the pong timeout later pings don't push it out (a truly half-open socket still trips). `heartbeat: false` disables it. Wire types `ping`/`pong` added.
- [x] **3.4 — Outbound throttle.** rAF-aligned (~60fps) coalescing of `update` sends (multiple param changes in a frame → one message). Per-component rate/opt-out prop.
  - *Note:* `setValue(v, { throttle: true })` on the binding buffers into one per-frame `update`; the optimistic local signal write stays immediate. `<RangeInput>` throttles by default with a `throttle={false}` opt-out; discrete controls (`NumberInput`, `TextInput`) send immediately.
- [x] **3.5 — Backpressure.** Check `ws.bufferedAmount` against a high-water mark before sending; skip `update`s while above it (latest coalesced value supersedes). Flip a `congested` flag on the status signal; sustained high-water → forced reconnect.
  - *Note:* `congested` is exposed as its own `Accessor<boolean>` on the connection (kept off the `status` enum so `status()` stays a plain lifecycle string). Sustained congestion past `backpressure.timeout` reconnects.
- [x] **3.6 — Disconnected sends + error handling.** Drop (debug-log) `update`/`pulse` written while `connecting`/`closed` — do **not** queue. Route inbound `error` messages to an errors signal / `onError` (console-log by default, non-fatal). Ignore unknown message `type`s; catch + drop malformed JSON without tearing down the socket.
  - *Note:* `error` wire type added; routed to `onError` + a `lastError` accessor. (`pulse` drop lands with the pulse message in Phase 4.3 — the update path already drops-and-logs while disconnected.)
- [x] **3.7 — Provider teardown.** `onCleanup`: close WS, cancel reconnect/backoff timer **and** ping interval, drop routing table + per-param signals. Each provider tears down only its own instance.
  - *Note:* `close()` cancels every timer (reconnect, watchdog, ping/pong, congestion, rAF frame), closes the socket, and clears the routing table. Timers go through an injectable `TDScheduler` (default = platform globals) so the timing paths are deterministically testable.

## Phase 4 — Remaining controls + parameter modes

Each control accepts a `name` prop, uses `createTDSignal`, passes through HTML props, and is a member of the `createTDClient<Schema>()` bundle. Mostly independent.

- [x] **4.1 — `Range`.** Slider with optional `min`/`max`/`step`; sends continuous values (throttled by default); reflects TD-side changes.
  - *Note:* already shipped as `<RangeInput>` in Phase 2.4/3.4 (the codebase settled on the `*Input` naming alongside `TextInput`/`NumberInput` rather than the proposal's bare `Range`) — no new work needed, just ticking the box.
- [x] **4.2 — `Toggle`.** Checkbox bound to a TD bool; sends `true`/`false`; bidirectional.
- [x] **4.3 — `pulse` message + `Button mode="pulse"` (default).** Add `{ type: "pulse", name }` to the wire types. Fire-and-forget, web→TD only, holds no state, **throttle-exempt** (sent immediately, but still respects backpressure — dropped + debug-logged into a congested socket). Excluded from snapshot/echo logic.
  - *Note:* `connection.pulse(name)` is a dedicated send path (not `signal()`/`setValue`) — no routing-table entry, no signal, so there's nothing for `applyParams`/echo-suppression to touch.
- [x] **4.4 — `Button mode="hold"`.** Momentary bool: `true` on press, `false` on release. Pointer capture on pointerdown; `pointerup`/`pointercancel`/`lostpointercapture`/window `blur` all → release. Keyboard Space/Enter (keydown→`true`, keyup→`false`, suppress key-repeat). Pressed-state ARIA. Normal bidirectional bool `update`.
- [x] **4.5 — `Button mode="toggle"`.** Each click flips a TD bool; same wire path as `Toggle`, rendered as a button.
  - *Note:* 4.3/4.4/4.5 share one `<Button mode="pulse|hold|toggle">` component (`mode` fixed at setup, like `TextInput`'s `commitOn`/`multiline`) rather than three separate components, matching the proposal's framing of one button with three wire behaviors.
- [x] **4.6 — `Select`.** Dropdown bound to a TD Menu par; `options` is web-authored `{ value, label }[]`; wire value is the menu string **key**; reflects TD-side changes.
- [x] **4.7 — `Vector`.** Group of numeric inputs bound to a non-color multi-component `number[]` ParGroup; `length` (or `labels`) prop sets component count; sends whole array (throttled while dragging); reflects TD. This is the generic array wire shape.
- [x] **4.8 — `Color`.** Color-specialized sibling of `Vector` bound to a `[r,g,b]`/`[r,g,b,a]` array (0–1 floats); `alpha` prop toggles RGB vs RGBA; throttled while dragging.
  - *Note:* renders a native `<input type="color">` (hex, RGB only) plus a separate 0–1 alpha range when `alpha` is set — the color input has no native alpha channel.
- [x] **4.9 — Multiple components per parameter.** Verify the shared-signal model: all binders of a name share one signal, optimistic writes fan out, focus-suppression count handles overlapping editors. Likely already satisfied by 2.5 — add explicit tests (slider + readout, slider + number input).
  - *Note:* added `components/sharedSignal.test.tsx` — confirms fan-out both directions (slider↔readout, slider↔number input) and that the editor count (not a boolean) keeps suppression active until every overlapping editor releases.
- [x] **4.10 — Read-only / parameter modes.** Web-side `readonly` set authored beside the schema → bound control renders disabled + dev warn. Handle inbound `param_not_writable` error → `markReadonly(ref)` + re-snapshot to revert the optimistic edit. No wire-format change.
  - *Note:* `<Provider readonly={[...]}>` forwards into `createTDConnection`'s `readonly` option; `TDBinding.readonly` is a reactive per-name accessor every bound control disables on (explicit `disabled` prop still wins). The runtime safety net lives in `handleError`: a `param_not_writable` marks the ref read-only and re-sends `snapshot-request`, so the optimistic edit that TD silently ignored snaps back once the fresh snapshot lands.
- [x] **4.11 — `TextInput` `commitOn`.** `commitOn` (`'input' | 'enter'`) + `onCommit` props; form-submit and Enter-fallback commit paths; blur commits; Escape reverts; no-op on unchanged value; `commitOn="input"` unregressed. Built for `apps/text-selector` (see [TEXT_SELECTOR.md](TEXT_SELECTOR.md)).
- [x] **4.12 — `apps/text-selector` phrase library → SQLite.** Migrated the phrase library
      (`tabs`/`recent`) off `localStorage` onto a `node:sqlite`-backed `/api/library`, mounted as a
      Vite plugin on the dev and preview servers; `activeTabId` stays in `localStorage` as UI state.
      Node engine requirement bumped to `>=24`. See [TEXT_SELECTOR.md §5](TEXT_SELECTOR.md#5-storage)

## Phase 5 — Video (WebRTC)

Signaling is multiplexed over the **same** WebSocket. `iceServers: []` (host candidates only on localhost). Tested against a faked `RTCPeerConnection`; real media is a manual check in Phase 6.

- [x] **5.1 — Extend wire types** for `rtc-offer`, `rtc-answer`, `rtc-ice`, `streams` (both directions).
  - *Note:* all four are members of **both** `ClientMessage` and `ServerMessage`, since the browser offers on connect/rebuild while TD offers on its own renegotiations. `parse` keeps `candidate: null` (end-of-candidates) distinct from an absent `candidate`, and preserves an explicit `null` `sdpMid`/`sdpMLineIndex` rather than collapsing it to omitted.
- [x] **5.2 — `createTDVideoStream(config)` core.** `RTCPeerConnection({ iceServers: [] })`; signaling over the WS; trickle ICE both ways including `candidate: null` end-of-candidates → `addIceCandidate(null)`; returns a `MediaStream` signal. **Resolve the open offer-role question** (browser vs TD offers) — whichever offers on connect also offers on rebuild.
  - *Note:* **resolved as browser-offers** (rationale in the open-question section below). Signaling rides the control socket through a new `connection.subscribe(listener)` hook, so the connection stays ignorant of peers. The peer is built on the **first `snapshot`**, not at construction — offering into a socket whose handshake hasn't completed would wedge it in `have-local-offer` with no answer coming — and since every reconnect also ends in a `snapshot`, that same hook is the WS-recovery trigger (5.6). Inbound ICE arriving before a remote description is queued and flushed after `setRemoteDescription`.
- [x] **5.3 — `streams` mapping.** Map each track `mid` → stream `id`; support multiple tracks per peer; re-send the `streams` map on **every** (re)negotiation so `<Video>` rebinds if `mid`s shift.
  - *Note:* tracks are stored keyed by `mid` (what `ontrack` reports) with the announced list as a separate signal, so replacing that list on a renegotiation rebinds every `<Video>` without disturbing the decoded media. Re-sending the map on each negotiation is TD's half of this (Phase 6.4).
- [x] **5.4 — `<Video stream="...">`.** Renders the selected stream (defaults to the primary when only one exists); underlying `<video>` is `muted autoplay playsinline` with prop passthrough. Several `<Video>` on one stream id share the one decoded `MediaStream`.
  - *Note:* `muted` is set as a **property**, not the JSX attribute — the `muted` content attribute only seeds `defaultMuted`, which does nothing for an element created after parse, leaving the video unmuted and so blocked from autoplaying. Video is opt-in per provider (`<Provider video>`): without it no `RTCPeerConnection` is created, which matters across up to 8 instances, and `<Video>` throws a pointed error.
- [x] **5.5 — Per-stream status + rebuild-on-fail.** Monitor `connectionState` (fallback `iceConnectionState`); `failed` — and `disconnected` after ~2s grace — trigger a full **rebuild** (new `RTCPeerConnection` + re-signal), not `restartIce()`. Per-stream status signal drives a "reconnecting" overlay.
  - *Note:* `streamStatus(id)` refines the peer status per stream — a peer that's `connected` but hasn't delivered *this* id's track yet reads `connecting`. Status stays `reconnecting` across a rebuild rather than dropping back to `connecting`, so an overlay doesn't flicker off while the replacement negotiates.
- [x] **5.6 — Renegotiation + WS-reconnect recovery.** Handle `onnegotiationneeded` throughout the peer's life. Media is **not** torn down on a WS blip — on WS reconnect, check each peer's `connectionState` and rebuild only dead ones. `negotiationPending` flag records negotiation requested while the WS is down; flush it on reconnect.
- [x] **5.7 — Faked `RTCPeerConnection` tests** for signaling + rebuild paths.
  - *Note:* `testing/mockRTC.ts` (peer + `MediaStream` + track fakes) drives `video.test.ts`. It fires `onnegotiationneeded` from `addTransceiver` like a real browser does, because the connection relies on that event — never on `addTransceiver` returning — to send its offer.
- [x] **5.8 — Video peer cleanup.** Provider teardown closes the `RTCPeerConnection` and calls `stop()` on every received track / `MediaStream` so the hardware decoder is freed.
  - *Note:* the same teardown runs on every **rebuild**, not only on unmount — otherwise each failure would strand a decoder. A monotonic `peerId` invalidates in-flight async signaling, so a late `createAnswer` can't send SDP for a peer that's already gone.

## Phase 6 — TD reference project + integration examples

Reference TouchDesigner project under `td/`, plus the end-to-end example app pieces. Python/TD callbacks kept as version-controlled text beside the `.toe`.

- [x] **6.1 — Registry module.** Python `friendly name → { op, par, type, writable }` map. `type` ∈ `bool`/`number`/`string`/`number[]`.
  - *Note:* `REGISTRY` in `td/config.py` (and the fuller demo copy in `td/config-example.py`) is a **hand-authored static dict**, not a dynamically built or introspected registry — each entry's `type` is a human-declared literal, not inferred from the backing par's actual TD datatype. `writable` is optional and defaults to `True`. It's the single source of truth 6.2's coercion, mode-guard, and menu logic all read from (`_pars`, `_read`, `_snapshot`, `_write`, `_refuse_write` in `td/webserver-callbacks.py`). `TODO.md` has an open item to go the *other* direction — auto-creating TD custom pars from `REGISTRY` — so today the registry describes the web schema by hand rather than TD deriving it or vice versa.
- [x] **6.2 — Read/write DAT callbacks.** Coercion both directions per the wire-type table (menus carry the string key; arrays map to a fixed-order ParGroup). Mode-guard on write: skip + emit `param_not_writable` if any backing par isn't `CONSTANT`; per-component check for arrays.
  - *Note:* **the mode guard protects TD's project, not just the user's edit.** The proposal assumed a write to an expression-driven par would quietly no-op; measured on 2025.33070, `par.val = v` **flips the par to `CONSTANT` and detaches its expression permanently** (the text stays in `par.expr`, unevaluated, and no Python error is raised). An unguarded web write therefore vandalises a TD author's work rather than merely failing. [TECH_PROPOSAL.md](TECH_PROPOSAL.md) § *Parameter modes* has been corrected to match.
  - *Note:* `pulse` is deliberately **not** mode-guarded — `par.pulse()` was measured to leave the mode untouched (an `EXPRESSION` par is still `EXPRESSION` afterwards), so it can't detach anything. It honours the registry's `writable` flag only.
  - *Note:* arrays now resolve through `base.parGroup[name]` instead of a `pars('Color*')` name glob. The glob was wrong twice over: it swept up unrelated pars sharing the prefix (a `Colormode` beside `Colorr/g/b/a`) and ordered by the operator's par list rather than by component. The ParGroup's own order *is* the wire array order. `broadcast_param_change` matches on the group's real components for the same reason.
  - *Note:* **an unknown menu key silently selects TD's first menu entry** — no exception — and the Parameter Execute DAT then broadcasts that back as if the user had chosen it. Since `<Select>`'s options are web-authored by design, drift is expected, so writes validate against `par.menuNames` first. This is the failure the "menus carry the string key" line was really guarding.
  - *Note:* one error code added, `param_type_mismatch` (wrong JSON type, wrong array length, unknown menu key), alongside the `missing_param` this file already emitted. `td-core`'s `parse()` accepts unknown codes and `handleError` acts only on `param_not_writable`, so it's surfaced non-fatally with no web-side change. Coercion is all-or-nothing per param: every component is converted before any is assigned, so a bad third component can't half-apply a colour.
  - *Verified* against the running `Example.toe`: full snapshot round-trip with correct JSON types; a refused write leaves the par in `EXPRESSION` mode with its expression still driving; a half-constant ParGroup is refused whole with the other components untouched; bad menu key leaves the par alone. Every frame the callbacks emit was fed through `td-core`'s compiled `parse()` and accepted, and `td-core`'s 145 tests still pass.
  - *Note:* **`menus` — one deliberate wire addition, and the only TD → web introspection in the protocol.** Driven by the audio-device dropdown in `apps/example`: an Audio Device In CHOP's `device` menu has machine-specific keys (`{0.0.1.00000000}.{feb5e51a-…}||Voicemeeter_Out_A4_(VB-Audio…)||1`) with separate readable labels, and the list changes when hardware is plugged in — so it is not authorable on the web at any price, which is the test for admitting a menu to this exception. `<Select>`'s `options` prop is now optional and always wins when present, so no existing select changes. TD announces every menu-backed `string` param (no registry flag — a par either has `menuNames` or it doesn't; `bool` params are excluded because TD Toggles carry `menuNames` too but render as checkboxes). See [TECH_PROPOSAL.md](TECH_PROPOSAL.md) § *TD-announced menus*.
  - *Note:* **two real `<Select>` bugs fell out of this, both invisible with a static option list.** (1) `<For>` recycles `<option>` elements in place, so a changed list kept the selected *index* while the values shifted underneath — the dropdown silently showed a neighbouring device as selected. Selection is now bound per-option (`selected={…}`), following the data rather than the position; an effect re-asserting `select.value` does **not** fix it, since it runs before `For` updates the DOM. (2) A value TD reports that has no matching option (device unplugged while selected) made `<select>` display some *other* option as though the user had chosen it; it now renders as a disabled "(unavailable)" entry, so the UI never misreports TD's state.
  - *Note:* **this is an open TouchDesigner bug, confirmed still present on 2025.33070**, not a gap in our design. Derivative logged it in April 2021 ([forum](https://forum.derivative.ca/t/breaking-binding-a-dropdown-menu-out-to-a-perform-ui/13123) — staff: "the menuNames and menuLabels members are changing so they should be dependable"). Measured directly here: a Parameter DAT with Menu Names/Labels output watched by a DAT Execute fires `onTableChange` **0 times** on a `menuNames` change and **1 time** on a *value* change of the same par — so the wiring is sound and the menu change genuinely doesn't notify. **Don't retry that route.** Jarrett's `MenuWatcher.toe` workaround from that thread is no help to us either: its mechanism is a manual Update pulse (what our Reload button already is) and its payload is syncing a *TD dropdown widget*, which we don't have — our dropdown is in the browser, so we only ever need to *read* `menuNames` at a moment of our choosing, which always works.
  - *Note:* menu *contents* changing has **no TD callback** — a Parameter Execute DAT fires on value/mode/enable/export, and plugging in an interface changes none of them (the value is untouched; only the set of legal values grows). Best option when it exists (from that thread): if a TD *action* rebuilds the menu — a Screen Grab TOP's Refresh Sources — hook that pulse via `onPulse` and re-announce, which is a true event needing neither poll nor button. Audio devices don't qualify: the OS changes that list, not a par. So something must look again, and there are two ways: **`menus-request`** (web → TD), driving the "Reload devices" button beside the dropdown via `connection.requestMenus()` — the default, since whoever plugged the device in is right there; and an optional **TD-side poll**, `broadcast_menus_if_changed()` on a slow Execute DAT, **not wired up by default** because it costs a `menuNames` read per menu par per tick forever. Both funnel through the same diff, so an unchanged list sends nothing. A real change is **broadcast to every client**, not just the requester — a new device is news for every open browser.
  - *Verified* live in Chrome against the running TD: 13 real devices announced with readable labels; selecting one in the browser set the exact GUID key on TD's par; changing it in TD updated the browser; a simulated unplug re-announced 12 options and left the selected-but-gone device visible, disabled, and still matching TD's value; the Reload devices button took the list 13 → 11 in place, with no page reload. Against the live module, a `menus-request` with nothing changed replies only to the requester while a real change broadcasts to all — one delivery to the requester either way. `td-core` is at 157 tests passing.
- [x] **6.3 — Handshake/snapshot/broadcast callbacks.** `hello`→`welcome` (with `protocol` + optional instance metadata), `snapshot-request`→`snapshot` (all exposed params), `update` broadcast to all clients, `ping`→`pong`.
  - *Note:* all four flows live in `onWebSocketReceiveText` (`td/webserver-callbacks.py`). `hello` replies with `welcome` carrying `protocol` and the WebGuiServer's `Identifier` par as instance metadata. `snapshot-request` answers `menus` (if any TD-announced menus exist) then `snapshot` with every registry-exposed, non-`pulse` param via `_snapshot()`. `update` writes route through `_write()`, whose success fires the Parameter Execute DAT into `broadcast_param_change()` → `_broadcast()`, which iterates the module-level `clients` set and sends to every open socket, not just the writer. `ping` replies `pong` directly. Unknown/malformed message types are dropped silently rather than tearing down the socket, so a newer web client can add message types without breaking an older TD project.
- [x] **6.4 — WebRTC signaling callback.** WebRTC DAT + Video Stream Out TOP wired; SDP/ICE relayed over the Web Server DAT's WebSocket; `streams` announce.
  - *Note:* split across two files by direction — `td/webserver-callbacks.py` takes `rtc-offer`/`rtc-answer`/`rtc-ice` inbound and owns the `connection ↔ client` map (signaling must reach the one browser owning a peer, not every client); `td/webrtc-callbacks.py` relays answers, local ICE, and the `streams` map back out, reaching the sockets through `send_signaling()`. The `mid` in `streams` is parsed out of the negotiated SDP rather than authored — the browser picked it when it built the offer, and a renegotiation can shift it.
  - *Note:* the WebRTC DAT's `onIceCandidate` passes `(candidate, lineIndex, sdpMid)` — the reverse of how the wire message reads, so those are named rather than passed positionally.
  - *Note:* **one Video Stream Out TOP serves one peer.** The TOP has a single connection par, so a second browser re-points it and takes the stream from the first. Multiple simultaneous viewers need one TOP per client — **decided in 6.7: single-viewer per instance, newest-wins, and the callbacks now say so out loud.**
  - *Note:* **`addTrack` is what puts the media in the SDP**, and must precede `createAnswer` — the docs say so explicitly. Attaching the Video Stream Out TOP does *not* substitute for it: the TOP's `webrtc`/`webrtcconnection`/`webrtcvideotrack` pars are menus that only *select among tracks that already exist*, so without `addTrack` the answer negotiates cleanly and comes back `a=inactive`. That failure is near-invisible — `connectionState: connected`, a live receiver, no error on either side, just no pixels. Pointing the TOPs at the track is therefore a separate step, deferred one frame so the DAT has cooked and published those menus; it feeds pixels and never touches the SDP.
  - *Note:* TD's built-in pars are **lowercase** (`webrtc`, `mode`); only custom pars are capitalized like `REGISTRY`'s. Getting this backwards fails silently.

## Open question resolved during Phase 5

**WebRTC offer role — resolved: the browser offers.** `createTDVideoStream` sends the initial SDP offer on connect *and* on rebuild, expressing its interest as `recvonly` video transceivers (v1 media is TD → web, so the browser contributes no tracks of its own).

Why this side: only the browser knows when it wants a peer — first sync, or a rebuild after a failure — and browser-offers needs no extra "please offer" message to prod TD into starting. That keeps the connect and rebuild paths byte-for-byte identical, which is the symmetry the question was really about.

TD still offers for its **own** renegotiations, and that isn't a contradiction: only an offerer can add m-lines, so a TD instance that starts a new track has to drive that exchange itself. Inbound offers are therefore handled for the whole life of the peer, and a collision with our own in-flight offer is resolved by the browser yielding (`rollback`, then answer). Because the catalog already carries `rtc-offer`/`rtc-answer` in both directions, none of this is a wire change.

The one thing still owed to Phase 6: if the reference WebRTC DAT turns out to insist on offering first, `offerRole: 'td'` flips the initial role in a single option — the answer path is already implemented and tested.
